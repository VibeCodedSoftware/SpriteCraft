## Choice of foundation

| Option | Result |
|---|---|
| Fork PixiEditor | **No.** C#/.NET and Avalonia: this machine has no .NET SDK, nothing else here uses it, and its LGPL-3.0 licence would bind the fork, which conflicts with keeping the project simply permissive |
| Fork Pixelorama | **No.** MIT is fine, but it is GDScript on Godot, so it can't share code with the other Craft apps |
| New TypeScript + React + Tauri app | **Chosen.** Same stack, backend and exchange folder as GameCraft, LogicCraft, ParticleCraft and WorldCraft. CPU compositor now, WebGL2 available for GPU effects |

Trade-off: a WebView is slower than native for huge canvases. Keeping the compositor in plain typed arrays means the hot
paths can move to WebAssembly or a GPU later without changing the document model.

## Open source rule

Nothing may enter this project that threatens its open source status:

- Dependencies shipped in the app must be permissive. `tests/licenses.test.ts` fails on anything else, and on any import
  from outside declared dependencies.
- No code from PixiEditor (LGPL), or from Aseprite or paid extensions. References are used for ideas and feature lists only.
- Palettes are generated by this project's code. `.aseprite` support is written from the published format description.
- **Phase 3 and the Smack Studio patent:** the patent behind Smack Studio's "patented" 2D-to-3D rotation is most likely
  US 11321899 B1, "3D animation of 2D images" (filed 2021-05-28). Its main claim takes a source pixel's position plus a
  depth value, rotates that point in 3D and draws the pixel at the new position. On 2026-11-07 Google Patents listed it
  as "Expired - Fee Related", lapsed effective 2026-05-03. SpriteCraft's rig works the other way round: it casts a ray
  from each screen pixel onto a solid and reads a drawing's colour there; source pixels are never moved. Lapsed patents
  can sometimes be revived, so confirm the status on USPTO Patent Center before a release. This isn't legal advice.

## Architecture

```
src/core     Document model, compositor, raster shapes, selection, transforms, palettes, effects. No DOM, fully tested.
src/io       PNG, GIF, .aseprite, .spritecraft, sprite sheets, Craft exchange. No DOM, fully tested.
src/editor   Editor state and history, tools, commands, storage, file dialogs.
src/ui       Viewport, panels, timeline, dialogs, docking.
```

Key decisions:

- **Immutable documents.** An edit makes a new Doc sharing unchanged cels, so undo is a pointer swap and costs only changed
  pixels. Linked cels are the same object.
- **Trimmed cels.** Empty space costs nothing, and moved art keeps its off-canvas pixels.
- **One write path.** Every tool writes through `Surface`, which applies selection, alpha lock and canvas bounds.
- **Dirty rectangles.** A stroke recomposites only what it touched; the GPU then scales the result with nearest-neighbour.
- **Whole-number device-pixel zoom,** so pixels stay even at Windows scaling such as 125%.
- **Own PNG code.** Canvas APIs premultiply alpha and alter colours in semi-transparent pixels.
- **Registries.** Tools, effects and commands register themselves, which is the base for plugins in Phase 8.
- **Exchange through existing formats.** Sprites go out as baked `craft.vfx` flipbooks, which the other apps already import.
  The only change to them is an optional `pixelArt` flag.

## Phase 2 design: tweens (`src/core/anim.ts`)

- **A tween is data, its frames are a bake.** A `Motion` holds keyframes per property, and the layer's original art is kept
  under its own key (`layer:src:motion`), outside every frame. The frames it covers are rendered from that art and marked
  `gen`. Re-baking deletes only cels that carry this mark, so a frame the artist painted over (which loses the mark,
  since painting writes a fresh cel) survives every later change. This is the line between generated and hand-made frames.
- **Keys sit on frame ids, not numbers,** so they follow frames that are dragged around. Timing still comes from frame
  order: inserting a frame inside a tween slows it down by one frame, as in a traditional timeline.
- **One rule for re-baking.** `Editor.commit` re-bakes a tween when its source art changed, or when frames, size or palette
  changed. Every edit passes through `commit`, so no feature has to remember to do it.
- **Pixel art first.** Rotation reuses the 8× Scale2x enlargement from Phase 1, so turned art gets clean edges with only
  existing colours. Positions snap to whole pixels by default to stop shimmer. Indexed sprites are snapped to the palette.
- **Easing** is a preset name, a step count or a cubic bezier (the same shape CSS uses), solved by Newton steps with a
  bisection fallback. Each key's easing times the segment that leaves it.
- **Effects over time.** The effect API gained `t`, the position in a run of frames (0 up to but not including 1), so a whole
  number of cycles loops without a repeated frame. Any registered effect can be animated: number and colour settings
  blend from start to end along an easing curve. Wave warp is the first effect built to use `t`.
- **Live brush** (`src/core/dynamics.ts`): a seeded planner decides each dab's place, size, turn and colour shift, so
  the logic is testable and a stroke is repeatable. Turning is limited to quarter turns and mirrors, which move pixels
  without resampling. Pen pressure counts only for `pointerType === 'pen'`, because a mouse reports 0.5 while pressed.
- **Wave warp** moves each output pixel to a single source pixel (nearest), so it never adds colours, and offsets round to
  whole pixels by default. Ripple mode pushes pixels along the radius. A radius limits it to a soft-edged circle.

## Phase 3 design: the rig (`src/core/rig.ts`, Rig panel)

- **Parts on a 3D skeleton.** Each layer is a part hung on a bone. Bones form a hierarchy and turn about their joints
  (Euler angles, X then Y then Z). Poses are keyframes per bone and axis, reusing the Phase 2 key and easing code; a
  `view` bone holds the camera's turn and tilt.
- **Parts are solids, sampled from screen space.** For each screen pixel a ray goes into the part's own space and is
  marched, then bisected, onto the solid: a ball, tube or box (reshaped by fullness, flat front, taper and lean), a flat
  card with thickness, or a solid carved where the front and side drawings' outlines overlap, with each row's
  cross-section rounded to fit both.
- **Colour comes from the drawings, chosen by angle.** Every drawing is a view from one direction. A part uses the drawing
  made nearest the camera wherever it sees the surface well, so a face never mixes features from two drawings. Steep
  surfaces get the row's plain colours (outline or most common colour), the back gets the back view or a back setting
  built from the drawing's colours. When the drawing is squeezed, a feature among the covered columns wins over plain
  colour, at the one pixel nearest to it, so eyes don't vanish or widen.
- **Pixel art rules.** At rest, facing front, every part is its drawing pixel for pixel (tests check this for every shape).
  Shading is three bands with a narrow ordered dither at band edges: at most two darker tones per colour, none at 0%.
- **Depth.** Parts are drawn back to front by the depth of their middle, so overlap changes as the character turns.
  Within a part the ray finds the nearest surface itself.
- **Bends inside a part.** A bend at a canvas row splits the part into pieces, each on its own bone (each bend bone a child
  of the one above). Every lower piece also carries half the limb's width in rows above its bend: at rest they sit exactly
  on the piece above, and bent they swing round to fill the outside of the joint, the classic cutout-animation joint.
  Pieces are rigid; there is no per-pixel blending between bones. Limbs are jointed near their top by default.
- **Posing by hand.** `boneScreens` gives every bone's joint and tip on screen for any pose and camera, so the preview draws
  the skeleton and hit-tests it. Dragging a bone turns it about the axis of its own that faces the camera most (Bend (Z)
  from the front, Tilt (X) from the side) and keys the current frame on release.
- **Renders are ordinary pixels.** Rendering puts frames on a new layer and hides the part layers, so the result can be
  retouched like anything drawn by hand. Parts with nothing drawn on a frame hold their latest drawing.
- **Tried and dropped:** a voxel turn of a single flat sprite (rejected as not what was wanted), flat paper cards (looked
  flat, vanished side-on), each surface point picking its own drawing (doubled eyes), and a whole-face dither (noisy).

## Phase 4 design: lighting (`src/core/light.ts`, Lighting panel)

- **Normals from shapes, not grey painting.** Each visible layer is its own shape; its height rises from the edge in a
  quarter circle over the "edge rounding" distance, upper layers a little higher, and brightness adds detail. Slopes
  (Sobel) become normals. They are stored as an ordinary layer in the common green-up encoding, so they can be painted
  (with the normal picker), exported as a PNG, or replaced by an imported normal map.
- **Lights** are point, spot or directional, with Lambert diffuse and a Blinn-Phong highlight. Point and spot lights
  fade as 1 - (d/reach)². Flicker is a repeatable per-frame noise. Position, height and intensity can be keyed.
- **Pixel art rules.** The total light's brightness (not each channel) is snapped to a number of steps, so coloured
  light keeps one clean ramp; an optional ordered dither mixes neighbouring steps at their edges; "palette only" snaps
  the result to the sprite's palette. Defaults favour clean bands (no dither) after the first test looked speckled.
- **Shadows** march from each pixel towards the light over a height map rebuilt from the normal map (slopes summed from
  the edges in four directions), so painted normals cast shadows too.
- **Renders are ordinary pixels**, like tweens and the rig: lit frames go on a new layer and the source layers hide.

## Phase 5 design: shaders (`src/core/shaders.ts`, Shaders panel)

- **A shader is an effect.** The Phase 1 effect API (a pure function over pixels with declared settings) is the shader
  API, so a shader can be applied once from the Effects menu or stacked live on a layer, and plugins add both the same
  way. Its context gained the frame, the frame count, what is drawn under and over the layer, and what was over it on
  other frames.
- **Live stacks run in the compositor.** A layer's `fx` list runs over its pixels each time a frame is drawn, so the
  canvas, playback and every export match. Because shaders can move pixels anywhere, a partial redraw renders the whole
  frame and cuts the region out. What a shader sees above its layer is drawn without shaders, so stacks never feed on
  each other. Number settings can be keyed per frame with the Phase 2 keys.
- **Water** uses the water layer's own pixels as its shape. Per column it finds the waterline, mirrors the scene across
  it with wave offsets in whole pixels, shows what is under it by the see-through amount, darkens with depth in steps,
  adds foam and sparkles, and spreads elliptical ripple rings from points where layers above touch the waterline (now,
  and on earlier frames for trails) or from points typed or clicked.
- **Custom formulas** are parsed by a small recursive-descent parser into closures. Only the listed names, operators and
  functions exist, and lookups use own properties only, so a formula from a file can't reach anything else.
- **Not GPU yet.** Everything runs on the CPU in typed arrays, about 2 ms for a 64×64 water frame. The effect interface
  doesn't depend on that, so a WebGL path can be added later for large canvases.

## Phase 6 design: particles (`src/core/particles.ts`, Particles panel)

- **No state between frames.** Each particle is worked out from its number: a hash of the number and the emitter's
  seed gives its birth time, place, speed, life and size, and its path is stepped from birth to the current age at 60
  steps a second. Any frame can be drawn alone, and a looping emitter repeats its births every loop, also counting
  particles from the loop before that are still alive. So the frame after the last is exactly the first. The loop is
  the length of the whole animation in seconds.
- **A system is a live layer shader** (`particles`, live only), so it reuses Phase 5's pipeline: compositing, playback,
  exports, the art under the layer for bouncing off, and the layer's own pixels as a mask. The effect context gained
  seconds into the animation and the loop length.
- **Pixel drawing.** Positions are floored to whole pixels; colours step along the ramp over life with no blended shades;
  fades drop pixels on a Bayer pattern by default; pictures turn only in quarter turns; palette snapping is optional.
- **ParticleCraft.** Its units are metres in 3D with Y up; here they are pixels in a front view with Y down, at 16
  pixels a metre. An export writes both the block graph ParticleCraft edits and the compiled layers GameCraft and
  LogicCraft play, using only block types ParticleCraft already has. An import reads the compiled layers.
- **Bake** runs the same effect for each frame into the layer's cels and takes the system off the stack.

## Phase 7 design: weather (`src/core/weather.ts`, Weather panel)

- **Same idea as particles, tuned for weather.** A live layer shader (`weather`) with no state between frames. Each
  drop or flake falls a whole number of times per loop (its speed is nudged to fit), so loops are exact, and picks a
  new column from a hash on each fall, so the pattern doesn't repeat within the loop.
- **Surfaces.** A drop's path is scanned from the top for the first solid pixel: the ground row, the weather layer's
  own pixels (puddles), or the chosen layers below. Live effects can ask the compositor for only some of the layers under
  them (`belowWhere`); by default weather leaves out layers that fill the whole canvas (a sky), other weather or
  particle layers, and layers baked from them (`Layer.bakedFrom`).
- **Depth.** Far, middle and near layers differ in speed, length, size, count and colour, never in see-through
  pixels, which broke streaks into specks. Far drops are hidden by solid art. A split puts near drops on their own
  layer at the top.
- **Snow settling** is drawn above every top surface open to the sky, with a noisy depth and a shaded edge; it can
  grow with the animation's progress instead of looping.

## Phase 8 design: nodes (`src/core/nodes.ts`, Nodes panel)

- **A graph is another live shader** (`nodes`) on a layer, so it plays, exports and bakes like the rest, and the
  editor stays optional. The brief asked whether PixiEditor's architecture would suit; SpriteCraft didn't fork
  PixiEditor (see "Choice of foundation"), so the graph is built on SpriteCraft's own effect API instead.
- **Two kinds of value.** Images (canvas-sized pixel arrays) travel on wires between ports. Numbers come from Time,
  Number and Maths, and drive any number setting through a link to the setting's key; that's how graphs animate.
- **Effects are nodes for free.** Every registered effect becomes a node with its declared settings, so shaders,
  colour adjustments, distortion and plugin effects all appear without extra code.
- **Evaluation** runs each node once per frame (memoised), refuses loops when wiring, gives missing inputs the layer's
  own pixels, and passes over a node that throws (its input goes straight through) while marking it in the editor.
- **Live effects reach the document only through their context:** what's below, chosen layers below, and a layer's own
  pixels (`layerPixels`), so graphs stay pure and testable.
- **Files** (`.spritenodes.json`) are checked on import: unknown node types, values of the wrong type and links that
  don't fit are left out.

## Phase 9 design: polish

- **Caching instead of GPU (for now).** Documents are immutable, so a shaded layer for (document, frame, options) never
  changes and is kept. Playback, scrolling and hovering then do no shader work; editing invalidates naturally because
  each edit makes a new document. Only the three newest documents keep results (undo history would otherwise pin them
  all), within a memory budget. While a stroke is drawn on one layer, other shaded layers can be shown as they were.
  GPU shaders remain possible behind the same effect interface; the measured CPU times didn't call for them yet.
- **Failures stay small.** A live effect that throws is skipped and listed in the Performance panel; a panel that throws
  shows its error inside an error boundary. Neither takes down the canvas.
- **Tutorials check real state** (tool, pixels, layers, frames, lights, effects) rather than button presses, on
  practice sprites opened in new tabs.
- **Installer.** A small Rust program (`installer/`) carries the app's files and installs per user into
  `%LOCALAPPDATA%\Programs\SpriteCraft`, with shortcuts through the Windows shell API and an Apps & features entry under
  HKCU. Its manifest asks for no elevation (Windows otherwise prompts for any program named "setup"). The uninstaller is
  a copy of it that runs from the temp folder so it can remove its own folder. Tauri's NSIS bundler and Windows'
  IExpress were considered: the first needs new tool downloads; the second would put Microsoft's closed-source stub
  in every installer, against the open-source rule.
